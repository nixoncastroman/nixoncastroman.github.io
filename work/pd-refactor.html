Case study 01 · NTT DATA

Forward-Looking PD Refactor

I rewrote the slowest part of a credit-risk pipeline that NTT DATA sells to Indonesian banks. Same results, 5.7× faster, and it no longer runs out of memory.

Role
Machine Learning Engineer Intern
Where
NTT DATA, Jakarta
When
Jan 2026 – Jan 2027
Stack
Python, Kafka, Oracle, PostgreSQL, statsmodels

5.7×faster: 91 min → 16 min

17×less memory: 8.7 GB → 0.5 GB

7+decimal places matching the old code

Context

Banks use this pipeline for IFRS 9 reporting. It estimates how likely borrowers are to default, adjusted for where the economy is heading. The slow part searches millions of combinations of economic variables (interest rates, inflation, house prices) for the best regression models.

What I did

  • Split the old code into 20 small steps. Each one is triggered by a Kafka message and reads and writes through one data layer that works with both Oracle and PostgreSQL.
  • Wrote a test harness that runs the old and new code on the same data and compares every output table. All 29 test cases match to at least 7 decimal places.
  • Sped up the model search by computing the cheap checks (R², t-statistics) directly instead of fitting a model for every candidate. Only the top 10,000 get a full fit. A 1.65M-combination run went from 91 to 16 minutes.
  • Fixed the memory problem by streaming candidates in batches of 100,000 and keeping only the best 30,000 in a fixed-size heap. Peak memory on a 24M-combination run went from 8.7 GB to 0.5 GB, and the chosen models are the same.

The code belongs to NTT DATA, so it isn’t public.
